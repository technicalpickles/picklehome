# OpenClaw spike — what to learn from the running instance

A spike is already running on the laptop: [`pickleclaw`](https://github.com/technicalpickles/pickleclaw), OpenClaw in an OrbStack VM. This is the list of things to **extract, measure, and decide** from it before writing the `docs/plans/` design doc and the on-host deploy. The point of the spike is to replace the SEO-guide guesses (which disagree on port/user/paths) with observed facts, and to validate the two things that are genuinely new vs. the existing agents: the **Ollama cloud wiring** and the **chat-channel front door**.

**Update (2026-06-30):** the spike diverged from this checklist's assumptions in two ways: it's `npm install -g openclaw` (not Docker), and it's backed by **OpenRouter** (not Ollama cloud). So it answers the *application-level* mechanics below (config, secrets, channels, UI auth, tool plugins) directly, but the **docker-image (§1), Ollama-provider (§4), and NUC-hardware (§7)** items still need their own pass — either by pointing the spike at Ollama/Docker, or with a fresh one.

Reading that directly resolved several schema/mechanism questions below that neither the runtime spike nor docs summaries could pin down — tagged inline as "source-confirmed." This is a real source read, not inference or a docs-page summary.

## 3. Config model (can it be repo-driven?) — substantially answered by `pickleclaw`

`homelab_07` strongly prefers source-controlled, declarative config over interactive state. Find out how much of OpenClaw is declarable.

- **Config file format + location:** `openclaw.json` (json5) at `~/.openclaw/`. Edited via `openclaw config get|set|patch|validate` (validated writes) and **hot-reloads live** (confirmed for `agents.defaults.*` — no restart). ✅
- **SecretRefs make it fully committable, not just "mostly":** a `secrets.providers` system resolves `exec`/`file`/**`env`**-sourced values at runtime (the `env` form, source-confirmed in `src/config/types.secrets.ts`, is what backs the `"${VAR}"` shorthand — pickleclaw only exercised `exec`/`file` hands-on, but all three are real), so the config file itself never needs a plaintext secret — see [`findings.md`](findings.md#verified-against-the-pickleclaw-spike-non-docker) for the mechanism. ✅
- **`$include` — now exercised hands-on on `pickleclaw` (2026-07-01), mechanism confirmed with two new gotchas.** A config value can be `{ $include: "./file.json5" }`, resolved from **inside the config directory**; `openclaw config get <path>` correctly resolves an included file's contents (verified against `tools.web.search`). Two things the source read alone didn't surface:
  - **`config patch`'s default merge mode does not "replace the whole containing key" the way a fresh write would.** Patching `{ $include: "..." }` onto an *already-populated* key (recursive-merge semantics) leaves the `$include` pointer sitting **alongside** the pre-existing literal keys in the raw file, not replacing them — both mechanisms of "the deploy's real committed config" need the target key to be either brand-new or explicitly flattened first, not just patched.
  - **Once a key carries a `$include` pointer, OpenClaw actively protects it from being flattened:** `config patch --replace-path <key>` on an `$include`-owned key fails outright — `Error: Config write would flatten $include-owned config at <path>; edit that include file directly or remove the $include first.` Good safety behavior, but it means retrofitting `$include` onto an already-configured live section isn't a one-shot `config patch`; you either edit the include file directly or null out `$include` first, then re-add it cleanly. For a fresh onboarded deploy (empty target keys), this isn't a problem — it only bites when converting an existing populated config.
  - Committed, read-only-mounted include files can still back specific top-level sections (`tools`, `mcp`, etc.); the root `openclaw.json` stays writable (onboarding needs to create it — see below) and merely points at the includes. Caveat (source-confirmed, not yet independently re-verified live): OpenClaw's own `config set`/`plugins install` writes-through to a single-file include target, so a read-only mount blocks CLI writes to that section (fine — changes flow through git + redeploy instead).
  - Applying the `$include` patch printed `Applied 1 config update(s). Restart the gateway to apply.` — consistent with the new-provider-auth restart requirement, though this message prints generically after any patch, so it's not conclusive proof `$include` changes specifically need a restart vs. hot-reloading.
- **Is first-run setup interactive or file-driven? Neither — and "skip onboarding" does NOT mean "boot from a static file."** `openclaw onboard` is interactive by default but fully scriptable via `--non-interactive --accept-risk` + flags (incl. `--gateway-bind loopback`), reading the API key from an env var — pickleclaw confirmed this bare-metal. **Source-confirmed for Docker too** (`src/docker-setup.e2e.test.ts`, `docs/install/docker.md`): even with `OPENCLAW_SKIP_ONBOARDING=1`, the setup script still runs `config set --batch-json` against an existing config — implying `OPENCLAW_SKIP_ONBOARDING` is for **re-running setup against an already-onboarded persistent volume**, not initial bring-up. The documented manual flow for a *fresh* container is: `onboard --mode local --no-install-daemon --gateway-auth token --gateway-token-ref-env OPENCLAW_GATEWAY_TOKEN --skip-ui --suppress-gateway-token-output` → `config set --batch-json [...]` → `docker compose up -d`. Same shape as pickleclaw's bare-metal approach. ✅
- **Env-var overrides for settings beyond the initial API key** — not yet exercised in either spike (pickleclaw only used `OPENROUTER_API_KEY` at onboarding time; all subsequent config changes went through `openclaw config set/patch`, not env). The official docs' "provider env vars override config files" footgun (noted in `findings.md`) is still unverified hands-on. Still open: which settings, if any, are env-overridable post-onboarding, for `.env.vars` design.

## 4. Ollama cloud provider wiring (the chosen backend) — wiring, basic tool-calling, and latency now live-tested; sustained-load behavior still open

This is new and load-bearing — validate it actually works end to end before committing. **`pickleclaw` switched chat + heartbeat from OpenRouter to Ollama Cloud on 2026-07-01** (OpenRouter stays configured for embeddings only — see the bullet below). Reading OpenClaw's source directly (`docs/providers/ollama-cloud.md`, tag `v2026.6.10`) resolved the *wiring* question and caught a real bug in the original plan; the switch itself is now live, and a follow-up round gave the model real tool-calling tasks (not just a chat round-trip):

- **How to point OpenClaw at Ollama cloud — corrected, not just confirmed:** `ollama-cloud` is a **first-class built-in provider id**, not something to hand-roll as a custom `models.providers` entry. Onboard with `openclaw onboard --auth-choice ollama-cloud` or just export `OLLAMA_API_KEY`; model refs look like `ollama-cloud/kimi-k2.6` (list the live catalog with `openclaw models list --provider ollama-cloud`). ✅ **Bug caught:** the original plan pointed a custom provider at the OpenAI-compatible `https://ollama.com/v1` endpoint. The docs are explicit that this is wrong — Ollama Cloud speaks its **native `/api/chat`** (base URL `https://ollama.com`, no `/v1`), and using `/v1` *"breaks tool calling and models may output raw tool JSON as plain text."* Still register the chosen model in `agents.defaults.models` + `agents.defaults.model.primary` (the model-registration trap from §3/pickleclaw applies here too — the official `config-tools.md` examples always pair these). ✅ **Live on `pickleclaw` (2026-07-01):** chat + heartbeat run `ollama-cloud/glm-5.2` (fallback `glm-4.7`, heartbeat `gpt-oss:20b`), all registered per the trap above; a smoke test (`openclaw agent --agent main -m "Reply with exactly: pong"`) round-tripped correctly (`executionTrace.winnerProvider: "ollama-cloud"`, replied `pong`).
- **Does the chosen model do tool/function calling well? — live-tested on `pickleclaw` (2026-07-01), looks solid.** Ran `openclaw agent --agent main --json -m "..."` with prompts requiring real shell tool calls (not just chat) against `ollama-cloud/glm-5.2`: a two-tool-call turn (`date` then `ls -la ~/.openclaw/workspace`) and two single-tool-call turns (`echo`). All 3 turns: `toolSummary.failures: 0`, correct tool (`exec`) invoked each time, and the model accurately reported the real command output back with no hallucination or raw-JSON leakage. Small sample (3 turns, 4 tool calls, simple shell commands only) — doesn't rule out weaker performance on more complex/ambiguous multi-step tasks, but the core mechanism (model → tool call → real result → accurate summary) works cleanly.
- **Latency per turn against Ollama cloud — measured.** Three consecutive turns: 73s (2 tool calls), 22s (1 tool call), 40s (1 tool call). Noticeably slower than a typical hosted chat API, but workable for an async chat-bot use case (not real-time). Small sample; no measurement yet under a heavier/longer task.
- **Request volume / rate-limit feel — no throttling observed, but only a light sample.** 3 agent turns run back-to-back within about 2 minutes, no errors, no visible slowdown/backoff. Doesn't confirm behavior under sustained always-on load (heartbeats + real usage over hours/days) — that's still an open question for subscription-tier sizing.
- **Embeddings need a second provider — resolved by a live test on `pickleclaw`.** Ollama Cloud only serves chat; its hosted `/api/embed` returns `401 unauthorized` for every model tried (six model names, ruling out a naming or proxy issue), and Ollama's own docs list `/v1/embeddings` as "Coming soon." Keep OpenRouter configured as a second provider for embeddings only — chat/heartbeat stay on `ollama-cloud`. Two provider secrets in the deploy, not one.

## 5. Channel / front-door auth (the real security boundary) — resolved, both Pairing and Allowlist now live-tested

This replaces the SSH key that gates the existing agents — get it exactly right. **Documented:** four DM policies — Pairing (default, time-limited approval codes), **Allowlist** (what we want), Open (`"*"`), Disabled. So the mechanism is known; the spike just exercises it.

`pickleclaw` wired Telegram on the **default Pairing policy** initially and confirmed: an unknown sender's first message auto-generates a pairing request instead of a chat reply; approve with `openclaw pairing approve telegram <code>` (codes expire 1h); the first approved sender is auto-set as command owner. Long-poll confirmed too — no inbound port, `channels status` shows `mode:polling`. So:

- **Telegram long-poll vs webhook** ✅ confirmed no-ingress (outbound poll only, no `docker port`/listening port needed for the channel itself).
- **Does the bot require any inbound ports at all** in long-poll mode? ✅ No — confirmed via the channel itself requiring no listener.
- **Allowlist itself — now live-tested (2026-07-01) with a real second sender.** Flipped `pickleclaw`'s `channels.telegram.dmPolicy` to `"allowlist"` with `allowFrom: ["8999645212"]` (the owner's own chat ID), restarted the gateway, confirmed the owner's own DMs still worked. Then a friend (a genuinely different, non-allowlisted Telegram account) messaged the bot: **hard reject confirmed — the friend saw complete silence, no reply at all.** Checked the gateway side too: the rejected message left **zero trace** — no `[telegram] Inbound message ...` log line, `channels status`'s `lastInboundAt` unchanged (still shows only the owner's last message), nothing in `openclaw pairing list telegram`. **Real operational tradeoff worth knowing:** Allowlist's reject is silent end-to-end, including for the operator — there's no log line or counter anywhere (at default verbosity) recording that someone tried and got blocked, unlike Pairing, which visibly creates a listable pairing request. Decision made: `pickleclaw` is staying on Allowlist going forward (not reverted to Pairing) now that it's proven correct.
- **Config key path — corrected via source read:** `dmPolicy`/`allowFrom` are **per-channel** fields (`src/config/types.channel-messaging-common.ts`, `types.base.ts`: `dmPolicy: "pairing"|"allowlist"|"open"|"disabled"`, `allowFrom: Array<string|number>`) — e.g. `channels.telegram.dmPolicy` + `channels.telegram.allowFrom`, matching pickleclaw's real working config. There is **no** global `session.dm.policy`/`session.dm.allow` key — the design plan's guess at that path is wrong. `session.dmScope` is a real but unrelated setting (session isolation, not the policy itself). ✅

## 6. Tool surface / capabilities

Decide the minimum viable tool set; we widen later (trust-grows-with-capability). **Documented:** secure baseline already denies `group:runtime`/`group:fs`/`group:automation` + `exec: deny/ask:always`; profiles `minimal`/`coding`/`messaging`/`full` (onboarding → `coding`); `tools.allow`/`tools.deny` with deny-wins. So shaping the surface is a config exercise, not a discovery.

**New from `pickleclaw`, not previously known:** ClawHub is OpenClaw's own package registry (`openclaw plugins search/install`, `openclaw skills search/install`, separate from npm) — worth checking for a ready-made plugin before hand-rolling an MCP server for a given capability. Also: **installing a ClawHub plugin requires a gateway restart to load** (verified for `@openclaw/brave-plugin` and the built-in `google` plugin) — this is a different code path from MCP servers, so don't assume the "MCP hot-add" claim below extends to plugins in general.

- **Confirm the spike's actual profile + effective tool list** (onboarding may have set `coding`, which is broader than we want) → the day-one blast radius. → inspect config / ask the bot what it can do; set to `minimal` + curated.
- **Turn the browser tool off** and measure the RAM delta (claim: ~8 GB → ~4 GB). → `tools.deny: ["browser"]`, watch `docker stats`.
- **Decide the sandbox stance:** tool-sandbox needs `docker.sock` (vs. our no-socket rule) — confirm whether we run gateway-containerized + default-deny instead, and whether `exec`/`fs` work acceptably without the Docker sandbox. → test a curated tool set with `sandbox.mode: off` inside the already-containerized gateway.
- **Can it call external commands we'd want** — e.g. the existing `just` CLIs (climate/locks/etc.)? Is there a custom-tool / function mechanism? → this is the actual *use case* question: what do we want it to *do*. → try wiring one read-only command.
- **Live pickup confirmed on `pickleclaw` (2026-07-01), no restart needed.** The gateway's actual exec-tool `PATH` (confirmed by asking the agent to `echo $PATH`, not just the SSH shell's) includes `~/bin` and `~/.local/bin`. Dropped a brand-new executable into `~/bin` while the gateway service was already running (`systemctl --user is-active` stayed `active` throughout, no restart), then asked the agent to run it by name with no other setup — it found and ran it immediately, correct output, first try. This is the bare-metal equivalent of the docker `OPENCLAW_EXTRA_MOUNTS` question — validates the underlying mechanism (agent's shell tool re-reads `PATH` fresh per exec call, no process-level caching) that the tier-1 bind-mounted-bin pattern for the Docker deploy depends on; the Docker-specific part (does a `-v` bind mount update live the same way a native FS write does) is a separate, narrower fact still worth confirming once there's a docker+NUC pass, but the risky unknown — "does OpenClaw itself need a restart to see a new PATH entry" — is now answered: no.
- **Does an MCP server (stdio or HTTP/SSE sidecar) attach without rebuilding/restarting the OpenClaw container**, and is its config declarative/committable? → validates the tier-2 decoupled-tools path. → wire one MCP server per the `bundle-mcp` docs and confirm hot-add behavior.
- **Are config and runtime state separable, or intermingled in one `~/.openclaw` dir?** → decides whether we can commit a clean config file or must treat a file inside the state mount as source-of-truth. → inspect the dir layout after setup (this is the §3 catch).
- **Nodes as a capability-delegation mechanism — live-tested on `pickleclaw` for peripheral capabilities, not for exec/host reach.** A companion device (the Mac) paired as a node exposes a command surface (`canvas.*`, `screen.*`, `location.get`, etc.) that the agent can invoke; a device holds `operator`/`node` roles independently, and every node command needs both the node's own declared capability and gateway-side allow/deny policy to agree (a third gate, the node's own `exec-approvals.json`, applies specifically to `system.run`). One real gotcha worth carrying over: a node capability can be gated by an app-level *setting* distinct from the OS permission that backs it (macOS Location: the OS grant alone doesn't make the node advertise `location.get` — the app's own Location Access picker also has to be set to something other than Off). **Still untested:** routing actual tool/shell execution to a node (`tools.exec.host=node`) for reaching picklelab-the-host or another box — `pickleclaw`'s node is paired for peripheral capabilities only, `tools.exec` is unset there, so nothing routes exec calls to a node yet. See [findings.md § Sandbox vs nodes](findings.md#sandbox-vs-nodes-different-tools-small-overlap).

## 7. Resource footprint (does it fit the 16 GB NUC?) — idle + startup measured directly on the real hardware; under-load numbers accepted as unmeasured

`pickleclaw` runs on a Mac (OrbStack VM), not the J3455 NUC, and isn't measuring `docker stats` (no Docker involved) — none of that transfers. Three things were checked instead, live, on 2026-07-01:

- **picklelab's actual headroom (SSH, real numbers, not an estimate):** `free -h` → 15Gi total, 1.8Gi used, **13Gi "available"** (the Linux metric that accounts for reclaimable cache — the more meaningful number than "free"). `nproc` → 4 cores, matching the J3455's spec. `docker stats --no-stream` across all ~9 running services (`obsidian-sync` ×2, `second-brain-agent` ×2, `woodpecker` ×3, `brineworks-agent`/`brineworks-server` ×2 each, `github-actions-runner`, `taskchampion-sync`) sums to **~1 GB RAM total**, all comfortably under 1% CPU at idle. So the real, current budget is ~13 GB available, not a tight squeeze against existing load.
- **OpenClaw's own idle footprint, off-hardware first (Docker Desktop on the Mac):** pulled the real image, ran it with a `--dev` auto-generated config (no real model provider, `--auth token --bind lan`), confirmed `/healthz` → `200`. Idle RAM: ~573 MiB, CPU ~0.24% at rest, only 12 PIDs — much lower than the community "~4 GB idle / ~8 GB with browser" claims in `findings.md`. Checked why: **the browser tool plugin is loaded at startup but the actual browser process (Playwright/Chromium) is not spawned until first use** (`docker exec ... ps aux` showed only the main `openclaw` node process, no browser subprocess) — so the community RAM figures likely describe an *active browsing task*, not baseline idle.
- **Same test, repeated directly on picklelab (SSH, real hardware, 2026-07-01) — the actual §7 question, answered.** Pulled the same image (`docker pull` on picklelab, digest matched the Mac's exactly), ran the identical throwaway `--dev` container on a spare port, confirmed `/healthz` → `200`, then removed it — no disruption to the ~9 real services running there. **Idle RAM: ~492 MiB** (comparable to, even slightly better than, the Mac's ~573 MiB — RAM usage transfers across hardware about as expected). **CPU at idle: ~1.35%** (vs. ~0.24% on the Mac — proportionally higher on the weaker J3455 cores, but still trivially low in absolute terms). **Startup — this is where the weak hardware actually shows:** container start to `[gateway] ready` took **~2.3 seconds** on picklelab, vs. **~243ms** on the Mac — roughly **9–10× slower**, as expected for a 4-core Celeron with no GPU vs. Apple Silicon. Still entirely acceptable for an always-on service that boots once and stays up (not a per-request cost).
- **Accepted as unmeasured, not pursued further:** RAM/CPU *under real agentic load* (a live model actually doing tool calls, not an unconfigured `--dev` instance) on the J3455 itself, and with the browser tool actively invoked rather than just idle-loaded. Closing this honestly would need a real Ollama Cloud key wired into a picklelab test instance, a working channel, and a genuine multi-step agentic task run long enough to see peak usage — not a throwaway few-minute container. Given idle numbers are already comfortable relative to the ~13 GB available headroom (see above), and the community's own worst-case estimate (~8 GB while actively browsing) still fits, this is being accepted as a residual unknown rather than a blocker — real usage after deploy will surface the actual number.
- **Combining both:** even the pessimistic "~8 GB while actively browsing" community figure fits inside picklelab's ~13 GB available headroom alongside the existing ~1 GB of other services. The budget question looks comfortably answered; what's still missing is the **actual footprint on the J3455 itself** — idle/under-load RAM *and* CPU on the real (much weaker) hardware, a genuine agentic-task-under-load measurement with a real model wired up (this test used no working provider), and true cold-boot timing on that CPU.

## 8. Networking / binding — bind mechanism corrected via source read

- **Force loopback bind — mechanism confirmed by `pickleclaw` (bare metal), but the docker answer is different and the design plan had it backwards.** `--gateway-bind loopback` at `openclaw onboard` is the bare-metal mechanism (pickleclaw, `ss -ltnp` showing only `127.0.0.1:18789`/`[::1]:18789`). **For Docker, source-confirmed (`docs/install/docker.md`, `src/config/gateway-control-ui-origins.ts`):** the real env var is `OPENCLAW_GATEWAY_BIND` (not `OPENCLAW_BIND`), and the value should be **`lan`**, not `loopback`. Reason: Docker's default bridge networking means a published port (`-p 18789:18789`) arrives on the container's `eth0`; a gateway bound to `loopback` *inside* the container is unreachable even from the host. `scripts/docker/setup.sh` defaults to `OPENCLAW_GATEWAY_BIND=lan` for exactly this reason. **The security boundary for Docker is the compose port mapping** (`127.0.0.1:18789:18789`, host-side), not the app's internal bind mode — the design doc's `OPENCLAW_BIND: loopback` env line would likely have made the deploy unreachable, not safer. ✅ (config key itself, `gateway.bind`, accepts `auto|lan|loopback|custom|tailnet` — confirmed in `src/config/types.gateway.ts`.)
- **Any second port / outbound connections we didn't expect** → egress awareness (it browses + calls an LLM; know where it talks). → watch connections during use. (Not yet observed in either spike.)

- **Health endpoints confirmed** (`/healthz`, `/readyz`) — just wire them into the goss smoke check; nothing to discover. → curl both.
