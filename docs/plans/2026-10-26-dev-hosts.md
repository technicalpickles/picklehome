# picklehome dev hosts

**Status:** design, approved in conversation 2026-10-26, nothing built.

**Goal:** a dev host is an OrbStack machine that every `just deploy-<service>`
recipe targets unmodified, created from a prebuilt golden machine in about a
minute and deleted without ceremony. App-specific setup combines services on
one host the way picklelab combines them. The first host runs openclaw and
brineworks-server.

**Why now:** the openclaw dev loop is a Compose project on the Mac's shared
Docker engine plus a dead OrbStack machine that only serves secrets files
through a flaky mount. It reaches brineworks through a socat forwarder and a
hand-edited `tailscale serve` entry on the Mac's own tailnet name, which
something else overwrote (pickleclaw taskwarrior
`4ca6042a-1cc5-48ff-bedb-387d6a31839b`). `deploy.sh` has never run anywhere
but picklelab. It took prod down for three minutes on an `EBUSY` from
`config set mcp.apps.*` (`de9acf6e-3d4f-451b-9f20-2af878a43c1a`), and
brineworks-server stayed down for six days after a reboot because its oneshot
unit had no `Restart=` (pickleclaw journal 2026-10-16). Four open tasks say
"verify on prod" because there is no other host
(`ebc2ab25-9da2-47c3-a642-c9f2dc5fcd6b`, `43db34f4-7012-4433-8f2f-8dcf61b7a44c`,
`785c13a5-f3c4-4770-975e-11b37f342dea`, `4f747df8-9a5c-4417-883e-d43780a8fbb1`).

**Research:** pickleclaw's
`docs/design/2026-10-24-dev-bot-orbstack-vm-proposal.md` (the dev versus
picklelab divergence table) and the OrbStack capabilities survey at
`pickleclaw/scratch/2026-10-26-orbstack-capabilities.md` (gitignored, on
Josh's Mac; turning it into a skill is pickled-claude-plugins taskwarrior
`adb74d45-8d84-4d19-89fe-2a72fc5a04cc`).

## What stays the same

- `.env.template` is the one source of secret references.
- `just deploy-<service> host=<name>` is the deploy command. The `host`
  parameter already exists on every recipe.
- picklelab's behavior. Its constants move into an identity file that
  reproduces them, and the proof is a deploy with an empty diff.
- The `_deploy-remote` guards for picklelab: clean tree, on `main`, pushed.

## What a dev host is

An OrbStack machine, Ubuntu noble arm64 by default, that meets the contract
picklelab meets: Docker, Tailscale, the sudoers allowlist from
`homelab/scripts/setup-deploy-access.sh`, a checkout at `/opt/homelab`, data
under `/srv/data`, and an op service-account token under `/etc/opt/homelab`.

OrbStack machines are not VMs. `systemd-detect-virt` reports `lxc`, every
machine shares OrbStack's kernel, and there is no `/dev/kvm`. systemd is PID 1
and `systemctl` behaves as on a real box, and the `woodpecker-agent` machine
already runs stock Docker 29 with no `daemon.json`. So the deploy path, the
units and Compose are faithful. Kernel-level behavior is not, and AppArmor is
the open case. picklelab is x86_64 on Ubuntu 24.04. OrbStack can create an
amd64 machine through Rosetta when an image misbehaves on arm64.

Two OrbStack facts the scripts must respect. A machine that is not isolated
gets OrbStack's Mac engine socket at `/opt/orbstack-guest/run/docker.sock`, so
a dev host must talk to its own dockerd. And `orb stop` with no machine name
stops all of OrbStack, so every recipe names the machine.

## How a service gets onto a host

Nothing is copied from the Mac but one ssh command. `just deploy-<service>
host=<name>` runs `cd /opt/homelab && git pull && homelab/services/<service>/deploy.sh`
on the host, and `deploy.sh` does the rest from the host's own checkout:

1. Sources `deploy-lock.sh` and, after this design, `host-identity.sh`.
2. Filters `.env.template` and the host overlay into the op-run templates
   next to the unit.
3. Makes the `/srv/data/<service>` directories and fixes their ownership.
4. Fetches the service's source checkouts at their refs, `/opt/pickleclaw`
   for openclaw's gog-mcp build and `/opt/brineworks` for brineworks-server.
5. Runs the one-time onboard when no config exists, then the config batches
   that run on every deploy.
6. Builds the images that build from source and pulls the pinned ones. On a
   dev host both are already in the golden, so this step is a no-op unless a
   ref or a pin moved.
7. Runs `tailscale serve --service=svc:<name><suffix>`.
8. Links the systemd unit, reloads, enables, restarts. The unit starts the
   containers through `op-run-dual.sh`, which resolves secrets with the
   host's 1Password token and runs `docker compose up -d`.

A dev host follows the same eight steps. What differs is the identity file's
values and the branch the host checks out in the ssh command.

## Host identity

Every host has an identity file in the repo at `homelab/hosts/<name>.env`,
selected by `hostname` at deploy time. It holds the non-secret facts that vary
per host:

- `HOMELAB_HOST_KIND`: `prod` or `dev`. The deploy guards read it.
- `HOMELAB_SERVICE_SUFFIX`: empty on picklelab, `-dev` on a dev host, so
  picklelab serves `svc:openclaw` and a dev host `svc:openclaw-dev`. Six
  Service names across five services use it.
- `HOMELAB_ENV_OVERLAY`: the per-host overlay template name, see Secrets.
- `HOMELAB_OP_TOKEN_FILE`: the service-account token path under
  `/etc/opt/homelab`.
- Source refs for services that build from a checkout:
  `BRINEWORKS_REF` for `/opt/brineworks` and `PICKLECLAW_REF` for
  `/opt/pickleclaw`. On picklelab both are `main`. On a dev host each is a
  branch, fetched from origin. A pushed commit is the unit a dev host
  deploys. Uncommitted trees are tested at the Compose layer, see The
  openclaw app layer.

A helper at `homelab/scripts/host-identity.sh`, sourced the way
`deploy-lock.sh` is, exports these. `deploy.sh` and the units read the
variables instead of the literals they hold today. The survey found nine
code-level mentions of picklelab across the eleven `deploy.sh` files, four in
openclaw, so the migration is small. Services other than openclaw and
brineworks-server get the identity treatment when someone needs them on a dev
host, not before.

picklelab's file reproduces today's values. The proof that the refactor is
correct is `just deploy-openclaw` against picklelab with an empty diff in the
container's config and the host's units.

## Secrets

`scripts/service-env` gains a per-host overlay. The overlay is a second
template, `homelab/hosts/<name>.env.template`, whose keys win over
`.env.template`. It carries only the values that define identity: the
Telegram bot token, the chat-ID allowlist, the gateway token, and the four
`*_HOST` values with their `-dev` names. Everything else resolves from the
picklehome vault as today. The 65 references into that vault stay where they
are.

A dev 1Password service account scoped to one small dev vault holds the
overlay values. A dev host's token cannot read prod-only items. The prod
account is unchanged.

## Workflow

Five `just` recipes in picklehome, plus the deploy recipes that already exist.

- `devhost-golden` builds a stopped machine named `picklelab-golden`: Docker,
  the Tailscale package, the three setup scripts, the `/opt/homelab` clone,
  the pinned openclaw image pulled, and the gog-mcp and goplaces-node images
  built. It reruns to refresh the golden when a pin bumps. Setup is a script
  run with `orb -m`, or cloud-init with `orb create -c`.
- `devhost-new <name>` runs `orb clone picklelab-golden <name>`, then applies
  identity: the hostname, the Tailscale login under a dev tag, the token drop,
  and the Mac-side ssh config entry plus the agent-ssh-relay allowlist entry
  for `<name>.orb.local`. A clone carries the golden's state, so none of this
  can live in the golden. The recipe refuses the name `picklelab`.
- `deploy-<service> host=<name>.orb.local` is today's recipe. The
  `_deploy-remote` guards stay as they are when `HOMELAB_HOST_KIND` is `prod`.
  For a dev host the recipe pushes the current branch, whatever it is, and
  the host runs `git fetch origin <branch> && git checkout -B <branch>
  origin/<branch>` in place of `git pull`. The clean-tree check stays, so
  what a dev host runs is always a commit you can name.
- `devhost-ls` lists dev hosts with their refs and deployed services.
- `devhost-rm <name>` runs `orb delete <name>` and removes the ssh and relay
  entries.

`orb clone` snapshots the source on OrbStack's shared btrfs disk and copies on
demand, so a clone is seconds and no disk up front. The machines run no sshd.
`ssh <name>.orb.local` reaches OrbStack's built-in SSH server, which is why a
dev host needs no `openssh-server` and why the relay allowlist is the only
thing between an agent session and a dev host.

## Networking

A dev host is its own tailnet node under a dev tag. Its Services carry the
`-dev` suffix, so service-to-service URLs come from the same `*_HOST`
variables as prod, with overlay values. The dev openclaw reaches the dev
brineworks-server over `svc:brineworks-dev` on the same box, exactly as prod
reaches `svc:brineworks`.

Dev hosts run with `machine.<name>.isolate_network: true`. The survey found
that the `openclaw` machine, which is `isolated: true` with
`isolate_network: false`, reaches the Mac's own sshd on `host.orb.internal`
and on the Mac's LAN IP. Isolation alone is not a wall around the Mac. With
brineworks-server on the host, nothing on a dev host needs the Mac's network.

## The openclaw app layer

This is where combining services lands. Deploying openclaw and
brineworks-server to one dev host gives the dev bot a brineworks over the
tailnet, so the socat forwarder in pickleclaw's `dev-vm/compose.yaml`, the
`tailscale serve` entry on the Mac, and the SSRF gotcha on
`host.docker.internal` go away.

The per-combo loop for testing a pickleclaw worktree against a brineworks
worktree stays a Compose-level loop. It runs on the dev host's engine through
`DOCKER_CONTEXT`, one Compose project per combo on portool ports, with the
worktrees bind-mounted through `/mnt/mac`. That work is the `devstack-*`
tasks in pickleclaw (`60a7139f-0d21-470f-a51b-cb09dec7a411`,
`2ddc8604-c34d-40c2-858f-f5318c2aa086`, `4893bcb3-fdc8-41f3-8701-c4671b3691d1`,
`96266633-26b2-467e-8e16-d8d751f7345b`, `c7ae4947-1f28-4090-8f8a-9290966cbdfa`).
It depends on one unverified OrbStack behavior: whether a process watching a
bind mount of `/mnt/mac` inside a machine sees Mac-side edits, which
`skills.load.watch` needs (`894fd268-2e84-4633-b5e8-bf47a36d6303`).

## Verification

Three proofs, in this order, before the design counts as done.

1. picklelab's identity file deploys with an empty diff. Run
   `just deploy-openclaw` and `just deploy-brineworks-server` after the
   identity refactor and compare the container config and the units before
   and after.
2. A fresh clone takes `just deploy-openclaw host=<name>.orb.local` and
   `just deploy-brineworks-server host=<name>.orb.local` unmodified, and an
   `openclaw agent -m "triage contacts"` turn on that host calls brineworks
   tools served by the host's own brineworks-server.
3. `devhost-new` through `devhost-rm` takes under five minutes wall clock,
   measured with `time`.

## Decisions made here

- The identity file lives in the repo, selected by hostname, not only on the
  box. Reviewable and reproducible beats hidden.
- arm64 noble by default. amd64 through Rosetta is a per-machine toggle for
  reproducing an image problem.
- Dev hosts are isolated from the Mac's network.
- No sshd in machines. The built-in OrbStack server plus a relay entry is the
  whole ssh story.
- No registry. A golden machine with images already pulled replaces it. The
  registry comes back only if refreshing the golden gets annoying.
- First host scope is openclaw plus brineworks-server.

## Open questions

- Does `machine.<name>.mounts` narrow `/mnt/mac` for a non-isolated machine,
  and does an isolated machine with `isolate_network: true` still get
  `/mnt/mac` at all? The per-combo loop needs the worktree mount; if isolation
  removes it, the per-combo projects run on the Mac engine instead.
- Does `orb import` accept a hand-built rootfs, and what is the export file
  format? Only matters if the golden should be shareable as a file.
- Is a machine's IPv4 stable across restarts? Moot while everything uses
  `.orb.local` names.
