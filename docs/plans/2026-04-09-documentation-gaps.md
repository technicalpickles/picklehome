# Lighting

Lutron Caseta and Philips Hue control via local bridge APIs.

## Commands

### Lutron Caseta

```
just lutron devices                    # list all devices with current state
just lutron status                     # quick on/off overview
just lutron on <device>                # turn on (name substring or ID)
just lutron off <device>               # turn off
just lutron set <device> <value>       # dimmer 0-100 or fan speed (off/low/medium/high)
```

### Philips Hue

```
just hue pair [<host>]                 # one-time bridge pairing (press button first)
just hue lights                        # all lights with state, grouped by room
just hue sensors                       # motion sensors with battery + temp
just hue buttons                       # tap buttons with last event
just hue scenes                        # scenes by room
just hue groups                        # rooms/zones with light members
just hue on <light>                    # turn on (name substring or ID)
just hue off <light>                   # turn off
just hue set <light> <brightness>      # brightness 0-100
just hue scene <scene>                 # activate a scene (name substring)
just hue status                        # overview: lights on, active motion
```

## Setup

### Lutron Caseta

Caseta uses TLS client certificates for local bridge communication (no cloud). The pairing process generates cert files that are stored locally.

**Env vars** (from 1Password via `.env`):
- `LUTRON_BRIDGE_IP`: bridge IP on LAN
- `LUTRON_KEYFILE`, `LUTRON_CERTFILE`, `LUTRON_CAFILE`: paths to TLS cert files in `lighting/.certs/`

The cert files are generated during initial pairing with the Caseta bridge. They don't expire. If you need to re-pair, see the [pylutron-caseta docs](https://github.com/gurumitts/pylutron-caseta).

**Library:** `pylutron-caseta` (local TLS connection to Smart Bridge)

### Philips Hue

Hue uses the local V2 API with an app key generated by pressing the bridge's physical link button.

**First-time pairing:**
1. Press the link button on the Hue bridge
2. Run `just hue pair` (or `just hue pair <bridge-ip>`)
3. Save the returned app key to 1Password (`Philips Hue` item, `api_key` field)
4. Run `just dotenv`

**Env vars** (from 1Password via `.env`):
- `HUE_BRIDGE_IP`: bridge IP on LAN
- `HUE_API_KEY`: app key from pairing

**Library:** `aiohue` (async, Hue API V2, self-signed SSL cert handling built in)

## Architecture

Both integrations follow the same pattern:
- `__init__.py`: shared bridge connection (`connect()`) and display helpers
- `*_cli.py`: CLI entry point (argparse, async dispatch)
- Module file (`caseta.py`, `hue.py`): command implementations

Device matching is fuzzy: partial name substring or exact device ID. Multiple matches prompt the user to be more specific.

## Module structure

```
lighting/
  __init__.py          # Caseta bridge connection, shared display helpers
  lutron_cli.py        # Lutron CLI entry point
  caseta.py            # Caseta device commands (devices, status, on, off, set)
  hue_cli.py           # Hue CLI entry point
  hue.py               # Hue bridge connection + all Hue commands
```
```

```markdown
## Auth Patterns

All integrations use the same general pattern: credentials in 1Password, injected into `.env`, loaded by `python-dotenv` at import time.

**Three auth styles exist in this repo:**

| Style | Used by | Token storage | Notes |
|-------|---------|---------------|-------|
| API key (static) | UniFi, Cloudflare Radar, Google APIs | `.env` only | No refresh needed |
| OAuth token (refreshable) | Ecobee | `~/.local/state/picklehome/ecobee-tokens.json` | PIN flow, auto-refresh on use |
| Username/password → session token | Yale, Aladdin, BlueAir | `~/.local/state/picklehome/<service>-tokens.json` | Token cached, re-auth on expiry |
| TLS client cert | Lutron Caseta | `lighting/.certs/` (key, cert, CA) | One-time pairing, certs don't expire |

**Token storage convention:** `~/.local/state/picklehome/<service>-tokens.json` with 0600 permissions.

**When adding a new integration:**
1. Store credentials in 1Password (`picklehome` vault)
2. Add `op://` references to `.env.template`
3. Use `python-dotenv` to load at import time
4. If tokens need refresh, cache them in `~/.local/state/picklehome/`
5. Model the CLI on existing `*_cli.py` patterns (argparse + async dispatch)
```

## Testing

Tests live in `tests/`, mirroring the source layout (`tests/climate/ecobee/`, `tests/garage/aladdin/`, etc.).

```bash
uv run pytest                              # all tests
uv run pytest tests/climate/ -v            # one module
uv run pytest tests/test_comfort_switch.py -v  # one file
```

**Patterns used:**
- `pytest` with `unittest.mock` (patch, MagicMock). No pytest plugins beyond core.
- No conftest.py: fixtures are per-file, close to the tests that use them.
- API responses are mocked at the client boundary (patch the HTTP call or library method, not internal functions).
- Pure logic tests (config parsing, mode switching) don't need mocking.
- No integration tests that hit real APIs. All tests run offline.
```
